## 一、核心思維：抽象與翻譯的雙重性

### 為什麼只會寫 code 還不夠？

各位軟工夥伴啊，你們應該多少都遇過這種工程師：**「只在乎 Ticket，不在乎產品。」**

這樣子的工程師夥伴的預設工作模式是：「Ticket 來了，按圖施工！」；最好你把細節一次講清楚、規則列個幾十條，全部整理到 ticket 中，然後他就能埋頭苦幹把任務做完。這樣錯嗎？不一定啦 XDD

但是，你一定會有對這樣子的工作模式會有這種感覺：

> **問題在於，他們對「系統/產品的本質上在解決什麼問題」其實不太上心。**

他不常主動追問：「這件事對使用者的意義是什麼？」也不常主動驗證：「這個解法真能解決你的問題嗎？」他只要能把工單做完，就覺得一切 OK。（嘆，難免啦，畢竟在有些公司中工作真的沒什麼成就感 XDD。）

但是我想和你說的是，其實：**AI 也是這樣。**

你**一旦下完指令之後，LLM 的預設行為就是——埋頭苦幹**。它會照**它的理解、它的腦補**，直接下去施工。它不會在乎你專案的目標、不會在乎產品的戰略定位，也不會在乎你的組織此刻真正要解決的問題是什麼。

於是會發生兩種常見的錯：

所以，**為什麼只會寫 code 還不夠？**

因為「只寫 code」這種工作模式，預設你永遠把事情定義得極其清楚之後，他才有辦法「正確施工」。

而現實世界裡，真正難的部分，就是:「把事講清楚、把規格講明白」。

這就是我們要學的「抽象與翻譯」：

到這裡，水球我想丟給你一個挑戰式提問：

> **你手上的規格，真的足夠讓一個「不參與任何會議的人或 AI」直接把功能做對嗎？**

如果答案是否定的，那問題不在工程師或 AI，問題在**規格**， 在於——「抽象沒有被建立」、「翻譯沒有被完成」。

**規格必須是「先抽象」、「後翻譯」的精準產出物**。

## 二、領域驅動設計：Problem ↔ Solution Domain 光譜

### 軟體開發橫跨兩個領域

在理解抽象的細節之前，我們先來看軟體開發橫跨的兩個領域：**Problem Domain（問題領域）** 和 **Solution Domain（解法領域）**。

**Problem Domain（問題領域）** 指的是：

所有能讓企業「解決問題、創造價值」的定義。

**Solution Domain（解法領域）** 指的是：

反正就是一些「如何用技術提出解法」的設計細節。

讓我用「**水球軟體學院課程平台 (Waterball Software Academy, WSA)**」的例子來說明這兩個領域的差異：

**Problem Domain 的視角**： 業務專家：「完課率是非常重要的！！！」 我們必須要能⋯⋯

**Solution Domain 的視角**： 技術專家：「噢，那實作上應該會是：⋯⋯」

看到了嗎？同一件事，在 Problem Domain 談的是「使用者需要什麼」，在 Solution Domain 談的是「系統如何實現」。

### 領域驅動設計：讓兩個領域的專家說同樣的語言

這兩個領域的差異，帶來了一個嚴重的問題：**業務專家和技術專家說著完全不同的語言**。

你看啊：

如果這兩群人說著完全不同的語言，就會出現「雞同鴨講」：

這就是軟體專案失敗的主要原因之一。

**領域驅動設計（Domain-Driven Design, DDD）** 就是為了解決這個問題而誕生的方法論。

DDD 是 Eric Evans 在 2003 年的經典著作《Domain-Driven Design: Tackling Complexity in the Heart of Software》中提出的。這本書影響了整個軟體工程界，至今仍是軟體架構設計的必讀經典。

Eric Evans 在書中這樣說：

> **"The heart of software is its ability to solve domain-related problems for its user. All other features, vital though they may be, support this basic purpose."**
>
> **（軟體的核心，是技術一定是為了解決業務中的問題。所有功能，無論多麼重要，都是支持這個基本目的。）**

**DDD 的核心理念很簡單：從問題領域和解法領域出發，嘗試讓這兩個領域的領域專家（業務專家/技術專家）講「同樣的語言」，如此一來，技術就能為業務而生。**

這個「同樣的語言」，在 DDD 中被稱為 **Ubiquitous Language（通用/普及語言）**。

但 DDD 有個問題：**就是它太抽象了**。

很多團隊讀完 Eric Evans 的書後，還是不知道該從哪裡下手。Ubiquitous Language 很好，但具體要怎麼建立？怎麼讓業務人員和技術人員真正在同一個語言上協作？

這就是為什麼我們需要更具體的方法。從 DDD 出發，接著，水球我主張一個關鍵的概念：**抽象 = 共同語言**。

為了建立這個共同語言，我們需要理解：共同語言的抽象層次有哪些？每一層應該如何定義？

這就引導我們進入下一個章節：Vision 金字塔。

> **此篇文全是水球我自己的整理，是多個不同方法論的融會貫通，網路上應該很難查到類似的理解路徑。**

## 三、先抽象：企業級抽象的層次 - Vision 金字塔

### 從 Vision 到 Code 的 8 層

承接上一章，DDD 強調要建立共同語言（Ubiquitous Language），讓業務專家和技術專家能夠在同一個語言上協作。

那麼，這個共同語言的抽象層次具體有哪些呢？

John Ferguson Smart 在《BDD in Action》這本書中，提出了一個經典的金字塔模型：

> **這個金字塔模型適用於任何一間企業。**

水球我當年讀到這個金字塔的時候，那種感覺就像是——**哇，豁然開朗！**

就像看到一個非常美味的漢堡一樣。你看啊，漢堡有麵包、生菜、肉排、起司、醬料、番茄...每一層都有它的角色，但重點不是每一層都要做到完美，而是：

> **層層連貫、彼此緊密、一致，才是一個好漢堡！**

這個金字塔也是一樣的道理。

很多團隊會犯一個錯：他們會在某一層特別用力（比如 Vision 寫得超級詳細），但其他層就隨便帶過。結果呢？就像一個漢堡只有肉排很厚，但沒有醬料、沒有生菜，吃起來很乾、很難吞。

或者相反，有些團隊直接跳過前面幾層（Vision、Goals 都沒寫清楚），直接就開始寫 User Story 和 Code。這就像只拿肉排和麵包做漢堡，你根本不知道這個漢堡要給誰吃、要解決什麼問題。

**水球我那時候就下定決心：以後我的公司裡面，面對這個抽象層次的金字塔，我就要像吃漢堡一樣，一口把全部咬下去！**

這個「漢堡」比喻的意思是：

這個金字塔描述了從最高層的願景（Vision）到最低層的程式碼（Code）的完整抽象層次。

書中是這樣說的：

> **"The feature injection hierarchy helps you organize requirements from high-level business goals down to low-level implementation details: Vision → Goals → Capabilities → Features → User Stories → Scenarios"**

> **"Each layer in the hierarchy serves a different purpose and involves different stakeholders"**

重點是：**每一層有不同的目的，涉及不同的利益相關者**。

再次強調：不是每一層都要寫得很多、文字一堆、很完整，而是要**確保這 8 層是連貫的、一致的**。

就像漢堡一樣，每一層都要能一口咬到，這樣才有卓越的體驗。

### 行為驅動開發：從 Features 往下的精準定義

在這 8 層中，有一個重要的方法論叫做**行為驅動開發（Behavior-Driven Development, BDD）**。

BDD 關注的是從 Features（第 4 層）開始，一路往下到測試/程式碼（第 8 層，底層）的這條路徑。

BDD 的基本實踐是：**用 Gherkin Language（Given-When-Then 語法）來精準定義系統該有的每一項行為規則，如此一來，我們就可以快速地把這些行為規則翻譯成測試程式。**

這就是 BDD 在領域驅動設計中扮演的角色：它提供了一個具體的手段，讓 DDD 的「共同語言」可以被形式化、變成可以執行的測試程式碼，來驅動出符合商業價值的程式碼！

這裡只是稍微交代一下 DDD 和 BDD 的關係。

從上述你應該可知兩者之間只是相輔相成，**DDD 在乎領域的共同語言（抽象），而 BDD 在乎的是怎麼把共同語言直接翻譯成系統可直接執行的測試程式碼（翻譯）**，僅此而已。

### Problem & Solution 並不是二分法，而是光譜

好，現在你理解了抽象的層次。但還有一個問題：**這 8 層在 Problem Domain 和 Solution Domain 中的定位是什麼？**

傳統的需求工程文獻（例如 Michael Jackson 的《Problem Frames》）會把它們當成兩個獨立的空間：

> **"We must distinguish clearly between the problem to be solved and the machine that will solve it"**
>
> **（我們必須清楚區分要解決的問題和解決問題的機器）**

這個區分很重要啦，但水球我認為有個問題：**它讓人覺得 Problem 和 Solution 是二元切分的，好像有一條清楚的界線。**

但實際上呢？從需求到實作是一個**連續的光譜**：

**Acceptance Criteria （功能的驗收標準）在光譜的正中間**——它既描述了問題（驗收標準是什麼），也暗示了解法（如何驗證）。

你看啊，這個光譜的概念很重要，因為很多團隊會搞錯：他們以為 Problem 和 Solution 是「非黑即白」的兩個世界，結果討論需求的時候一直在跳來跳去。

### Solution 的兩種層次

特別要注意的是：在第 7 層（Examples）之間，Solution 層次分成兩種（**這是這門課最重要的知識，網路上甚至查都查不到，因為是水球我提出的概念**）：

1. **高階業務流程及規則解法**：制定如何解決問題的流程、規則、效率
2. **技術及機器程式碼解法**：程式碼如何在機器上運作

為什麼前者稱之為 DSL-Level Examples，而後者稱之為 ISA-Level Examples 呢？

首先，Martin Fowler 在《Domain-Specific Languages》中這樣定義 DSL：

> **"A Domain-Specific Language is a computer language that's targeted to a particular kind of problem"**
>
> **（DSL 是針對特定問題領域設計的語言）**

DSL 的重點是「targeted to a particular kind of problem」——它還是在描述問題領域，但是是為了提出業務上的解法而收攏的「共同語言」。

白話文來說，DSL 就是「行話」啦，是「一說出來就能被全體業務人員聽懂」的「共同語言」。

那 DSL-Level Examples 指的就是「用行話構成的場景/測試案例」。

而 ISA Level 則是：

> **"基於 Tech Stack 設計出來的指令集，耦合測試框架，可直接翻譯成程式碼"**

ISA 已經完全進入技術領域了。 而 ISA-Level Examples 指的就是「對應到不同技術領域下、自動化測試技術的場景/測試案例。」

#### 水球我踩過的坑：工程師太容易沉浸在 Solution 裡

工程師總是有一個問題：**太容易沉浸在 Solution 裡面**。

你看啊，當我們想到某個技術解法的時候，會覺得很好玩、很值得一試，然後就開始越講越多跟 Solution 的細節：「這樣好像就能動起來了欸！」、「可以啊，這個做得到，能用某個架構⋯⋯」、「自動化是可行的！只需要先⋯⋯」。

但大家往往都會忘記問一個很掃興的問題：

> **我們在解決的 Problem，到底是不是重要的 Problem？我們值得用多少時間去解決它？**

這個問題很掃興，所以很多工程師（包括我自己）心裡也許有數，但都會不小心忘記去檢驗「這個 Problem 到底重不重要」。

**舉個實際案例：客服系統的過度設計**

之前在做客服的時候，我就想要把 Messenger、LINE 官方帳號、Discord 這三個客服渠道整合起來，做一個自動化系統。不管使用者在哪一個頻道上面留言，我們都用同一個 agentic 的處理方式去回覆。

我那時候超興奮的，腦子裡全是「整合工程」、「統一處理邏輯」、「自動化回應」這些 Solution。

結果呢？我們行銷夥伴冷冷地說了一句話：

> **「還是我們全部統一用 LINE 官方帳號回覆就好了啊。」**

那句話一講出來，就是十分掃興啊，對啊！我幹嘛花那麼多時間去做整合工程？你先統一管道，看看狀況怎麼樣再說嘛。**確定一個 Problem 真的存在，你再動用 Solution 去解決它。**

這就是「過早進入 Solution」的典型案例。在軟體設計領域，這被稱為 **Over-design** 或 **Over-engineering**。

（這也是水球我的另一門課《軟體設計模式精通之旅》中非常重要的議題。）

**所以，這正是為什麼我們要很在乎 Problem/Solution Domains 之間的對等、一致性。**

你得先確認 Problem 是真實存在、值得解決的，再去思考 Solution。而這個光譜的概念，就是在提醒你：不要跳太快。

## 四、從抽象 Problem 到具象 Solution：規格的光譜

### 我們學了什麼？DDD、BDD、SDD 的關係

讓我們快速回顧一下到目前為止學到的內容：

現在，讓我們來看規格驅動開發（Specification-Driven Development, SDD）如何在 AI 時代把這一切推向全自動化。

### 三種方法論的遞進關係

在深入 規格驅動開發（Spec-Driven Development) 之前，我們需要理清這三個方法論的層次關係：

1. **領域驅動設計（DDD）** - 最大層次
2. **行為驅動開發（BDD）** - 中間層次
3. **規格驅動開發（SDD）** - 最具體層次

**SDD 如何借鑑 DDD 和 BDD，並向前推進？**

**水球發明的 「SDD」（你可以稱之為水球流 SDD，或是規格驅動全自動開發術）同時繼承了 DDD 和 BDD 的精華，但進一步將它們「落地」到 AI 時代。**

這就是為什麼這門課要從 DDD 的框架開始教起。因為只有理解了 Problem Domain 和 Solution Domain，理解了 Vision 金字塔的 8 層，理解了 BDD 如何用 Gherkin 形式化行為，你才能理解「規格」在 SDD 中扮演的完整角色。

### DSL Level：業務語言的可執行規格

在需求層（Features/User Story/AC）建立清楚後，下一步是把它們翻譯成**可執行的規格**。

這就是 **DSL Level（Domain-Specific Language）**。

Martin Fowler 在《Domain-Specific Languages》中定義：

> **"A Domain-Specific Language (DSL) is a computer language that's targeted to a particular kind of problem, rather than a general purpose language that's aimed at any kind of software problem"**
>
> **（DSL 是針對特定問題領域設計的語言，而不是通用語言）**

> **"The key characteristic of a DSL is that it is focused on a limited domain"**
>
> **（DSL 的關鍵特徵是它專注於有限的領域）**

在 BDD 中，我們常用 **Gherkin Langauge （Given-When-Then 語法）** 來收斂 DSL。

第一章中已經先讓大家體驗過 Gherkin Language，甚至也學過整個模型有哪些語法了。

### 結果導向的語言 vs. 過程導向的語言

好不好奇，為什麼水球將這種明確指出技術場域的 Examples，稱之為 ISA-Level Gherkin or Feature File?

其實啊，ISA 全名是 Instruction Set Architecture，這個詞原本指**計算機架構中的「指令集架構」**。

以前的組合語言都有所謂的指令集，高階語言只要被編譯成組合語言，就能被當成機器看得懂的指令來執行。

我們借用這個概念，類比到測試規格的層次：「**DSL-Feature 類比高階語言，ISA-Feature 類比組合語言，Test/Code 類比機器碼**」。 如此一來呢，DSL → ISA → Test/Code 就如同 高階語言 → 組合語言 → 機器碼 之間的關係，有沒有發現？

DSL 本身要被翻譯成「技術框架看得懂」的語言，所以 DSL 要先被翻譯成 ISA，然後 ISA 才能被翻譯成用「技術框架」來實現的 Test code 執行。

你如果將整條翻譯鏈子串起來，看起來會長這個樣子：

「**DSL-Level Feature → ISA-Level Feature → Test/Code → 高階語言 → 組合語言 → 機器碼**」

有沒有發現，AI 出來之後，工程師並不是要被取代，而是要開始去學習「比高階語言更高階」的語言了。

以前我們寫的語言屬於「過程導向」的語言，描述的都是執行過程的邏輯：「高階語言 → 組合語言 → 機器碼」 在 AI 時代下，我們要寫的語言就是「結果導向」的語言，描述的都是期望要驗證的結果：「DSL-Level Feature → ISA-Level Feature → Test/Code」。

這件事難道不會讓你興奮嗎？

有沒有發現，我們工程師並不是被取代，而是以前計算機的歷史（先有組合語言再有高階語言）現在又要重演一次（先有 ISA Gherkin 再有 DSL Gherkin)。

**你不會被取代，但你必須轉型，去寫「結果導向」的語言。**

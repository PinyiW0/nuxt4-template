### 領域驅動設計：事件風暴

你可能會好奇，那麼 DDD（Domain-Driven Design，領域驅動設計） 和 事件風暴之間的關係又是什麼？為什麼談到 Event Storming，總是會跟 DDD 一起出現？

讓我們先簡單回顧一下 DDD 的核心理念：**讓問題領域的專家（業務人員）和解法領域的專家（技術人員）能夠說出共同語言，一起建立對業務的理解**。

但問題來了——DDD 在 2003 年被 Eric Evans 提出時，雖然理念很好，但做法還是太抽象、太仰賴傳統的系統分析能力。對於非系統專業人員而言，上手門檻很高，很難真正參與建模。

**Event Storming 就是為了補足這個溝通短板而誕生的**。

因此，DDD 社群現在普遍推崇：**先學習比較簡單的 Event Storming，再深入理解 DDD 的其他概念**。Event Storming 成為了備受推崇的 DDD 思維切入點，讓 DDD 的學習門檻大幅降低。

所以當你聽到 Event Storming 時，要知道它不是憑空出現的，而是 DDD 這套成熟方法論中，最容易上手、最實用的協作工具！

### 事件風暴模型的核心洞察：事件（Event） 是切入點

Event Storming 模型提出了一個非常聰明的洞察：

> **「要怎麼樣讓一個房間內的所有人，都能簡單切入來理解一道系統流程？——透過 Event（事件）切入就行。」**

Event Storming 的作者 Alberto Brandolini 在描述這個方法時強調：它是「a workshop-based method to quickly find out what is happening in the domain」——**以協作式工作坊為基礎的實踐方法，讓會議中的所有人都可以快速找出領域中（或整個業務流程中）發生了什麼事，以及我們應該要怎麼去實作**。

重點就在這個「**what is happening**」指的是發生了什麼事，而不是如何做。

好比說，大家關心的，應該會是底下這些事件，因為這些事件都對課程平台的業務帶來好處：

這些 Event 描述的是「**使用者在業務流程上的進展，而這些進展對公司有幫助**」。 同時啊，在技術上還象徵著「**系統狀態的重要改變**」。

因此，無論是業務專家還是技術專家啊～這些「Event」就會是會議間內所有人都關注的事，因為不管你是用業務視角還是技術視角來看，Event 都是你認為的，有興趣的改變。

所以在 Event Storming 的實踐會議中，第一件事就是針對我們想要建模的系統，去盤整所有 Event，這也是為什麼這個方法被稱之為事件風暴 (Event Storming) 了！

### 事件 (Event) 還代表系統的可能邊界

另外一點，Event 還有一個很重要的性質：「**Event 代表系統的可能邊界**」。

這裡要特別說明一下，因為這個概念很重要，卻常被忽略。

當一個公司或專案啟動時，很多業務流程一開始都只是「構想」或「人工作業」，還沒有開發軟體來支援。舉例來說：

那麼，**公司要如何決定哪些流程需要開發軟體來自動化？哪些流程值得投入開發資源？**

答案就是：**從 Event 切入！**

你想想看啊，「學生完成了課程」這個 Event，代表什麼？

既然這是一個「大家都有興趣、對業務有幫助」的事件，那我們就「可能」需要仔細思考：**是否要開發軟體來自動化運作這件事？**

這就是系統的邊界——Event 幫助我們識別出：哪些地方需要開發軟體來運作、來實現自動化流程。

**Event 是找到系統邊界的切入點，指導公司決定開發哪些軟體。**

所以，Event Storming 模型以 Event 作為切入點，讓大家聚焦在：

這就是 Event Storming 模型的關鍵——用 Event 作為橋樑，連接兩個世界。

## 二、Event Storming 模型的核心元素

好，現在我們知道 Event 是切入點。那麼，從 Event 要如何展開？

Event Storming 模型定義了六個核心元素：**事件 (Event)、操作 (Command)、查詢模型 (Read Model)、執行者 (Actor)、規則 (Rules)、聚合 (Aggregate)。**

來，讓水球我一個一個帶你看。

我們先單點單點理解每一個核心元素的「定義」，最後再把所有元素拼起來，拼成一個超級易於理解的「系統模型」。

先快速讀一下每個元素的定義和描述吧！

### 元素一：Event（事件）

**定義**：系統狀態的改變，無論是業務專家還是技術專家都有興趣的「改變」。

**特性**：

**範例（WSA 課程平台）**：

你會發現，這些 Event 都是用「**過去式**」描述的。因為 Event 是「已經發生的事」，不是「將要發生的事」。

而且啊，這些 Event 都是業務人員關心的。

業務會問：「學生的完課率怎麼樣？學生完成課程後進度能被追蹤嗎？」 QA 會問：「完成課程的前提是什麼？完成後會發生什麼事？」 工程師會問：「得知課程完成後，系統要做什麼？」

大家都在討論同一個 Event，只是關注的層次不同。這就是 Event 作為切入點的價值。

### 元素二：Command（命令）

好，Event 發生了。那麼，Event 是怎麼來的？

答案是：**Command（命令/操作）**。

**定義**：Actor 對系統執行的操作、Actor 與系統的互動所在之處。

**特性**：

**範例（WSA LessonCompleted）**：

我問你啊，「學生完成課程」這個 Event，它對應的 Command 是什麼？

許多夥伴可能會天真地推論：

「嗯，『學生完成課程』這個 Event ～ 啊不就是透過使用者 『完成課程』才觸發的嗎？那它對應的 Command 不就是「完成課程 (`CompleteLesson`)」嗎？」

「感覺就只是把 Event 的過去式，改成主動式，就變成 Command 了啊，就像是『我已經吃完早餐了』這個 Event 不就是來自於『吃早餐』這個 Command 嗎？」

呀，萬萬不是！！

在 WSA 課程平台中，學生完課（進度達到 100%）的方式有很多種，根據不同單元類型，會有不同前提：

你看到了嗎？**三個不同的 Commands，都可能帶來同一個 Event：完課 (`LessonCompleted`)**。

這就是 Event 和 Command 的顆粒度差異。Event 關注的是「發生了什麼重要的改變」（業務語言），Command 關注的是「如何操作」（功能語言）。

那當然，**Event 要抓得多細，就是看全體人員共識決定**，好比說如果你想要設計一個 Event 叫做 觀看影片的進度已增加 (`VideoProgressUpdated`)，那當然也是可以，其對應的 Command 就是增加影片進度 （`AddVideoProgress`）。

雖然 Event Storming 完全允許你任意調整顆粒度，讓 Command 和 Event 總是成雙成對出現。但本質上，兩者之間的顆粒度就是不同，畢竟 Command 是角色與系統的互動所在，Event 則是大家興趣所在的代表元素，Event 數量會 <= Command 的數量。

記清楚了嗎？這便是為什麼我們提倡先從顆粒度較粗的「Event」下手來分析系統，**Event 的數量較少，卻最容易凝聚所有人員的共識，也較容易開始**。

### 元素三：Actor（角色）

Command 不會憑空出現，一定有人（或系統）執行它。

**定義**：執行 Command 的人或系統。

**範例**：

Actor 可以是**人**，也可以是**系統**。重點是：誰觸發了這個 Command？

人可能是藉由前端與系統互動，來觸發 Command，而其他系統可能是因為上下游的依賴關係，而觸發 Command。

總之，人和系統都可以是執行 Command 的 Actor。

### 元素四：Rules（規則）

Command 不是隨便就能執行的，它需要遵守一些條件。

**定義**：Command 在執行時要遵守的前置條件和後置條件。

**對應到 Vision 金字塔**：**Acceptance Criteria**（第 6 層，正中間）

Rules 分成兩種：

「前置條件」和「後置條件」這部分其實是水球我自己整理的知識。

我將 Event storming 的 Rule 概念整合了 Bertrand Meyer 提出的 Design by Contract 概念。他在 1997 年的經典著作中寫道：「A precondition binds the clients; it defines the conditions under which a call to the routine is legitimate.」

1. 前置條件就像合約條款，規範了什麼情況下可以執行這個操作。
2. 而對於後置條件，Meyer 的定義同樣精準：「A postcondition binds the supplier; it defines the properties of the state resulting from the routine's execution.」白話來說，**後置條件約束供應方（系統），它定義了執行後系統應該達到的狀態**。

## 三、從 Event 展開的判斷順序

好，我們認識了六個核心元素。現在讓我們看看，這些元素是如何從 Event 展開的，思考順序是什麼？

### 展開流程

這個流程中有一個重要的決策點：**確認需要軟體支援後，展開其他元素來制定規格**。

為什麼這個決策點很重要？因為不是所有 Event 都需要開發軟體來支援。有些 Event 可能只需要人工處理，或者可以用現成工具解決。只有確認需要客製化軟體支援的 Event，我們才需要深入展開 Command、Rules、Aggregate 這些元素。

這樣可以避免過度設計，把精力集中在真正需要軟體支援的地方。

讓我一步一步解釋這個流程。

#### 步驟 7：Actor 如何知道當前狀態？→ Read Model

我們剛剛看到從 Event 可以展開出 Command、Rules、Aggregate。但實際上，流程不會只有一個 Command。

Actor 在執行 Command 之前，需要先知道「當前系統的狀態是什麼」，才能做出正確的決策。

```
          ↓
Actor 根據查詢結果做決策
          ↓
Actor 執行 Command
          ↓
Command 改變 Aggregate 狀態
          ↓
raise Event
          ↓
Actor 又需要查詢新的狀態 (Read Model)
          ↓
循環...
```

這就是 **Read Model → Command → Aggregate/Event → Read Model** 的連續關係～！

讓我們逐步拆解。

#### Step 1：查詢挑戰題 → 提交作業

**1.1 Read Model：查詢挑戰題要求**

Alice 想要開始挑戰題作業，首先需要查詢挑戰題的要求。 參考完挑戰題的作業要求後，才有辦法開始下去寫作業，寫完才能提交作業檔案。

因此你的事件風暴模型可以長成這樣：

```
[Read Model]                    [Actor]         [Command]
GetChallengeRequirements  →   學生 Alice   →  SubmitChallenge
查詢挑戰題要求                               提交作業
         ↑ 根據                    ↓ 執行
```

**1.2 Command：提交作業**

那麼在提交作業之後啊，接著，系統會去看說本次提交是否有符合規則，如果有的話，就會改變系統狀態，新增此筆作業提交的狀態聚合，最後產生「作業已提交」的事件。

```
[Command]              [Rules]                    [Aggregate]
SubmitChallenge  →   Preconditions:          → ChallengeSubmission
提交作業              • 學生有課程權限           • userId: Alice
                      • 尚未提交或可重新提交      • challengeId: 101
                      • 作業內容不為空           • status: SUBMITTED
      ↓ 通過：改變狀態                                ↓ 產生
                                                  [Event]
                                              ChallengeSubmitted
                                                作業已提交
```

#### Step 2：老師查詢提交 → 批改

**2.1 Read Model：老師查詢學生提交**

老師 Bob 收到通知，Alice 提交了作業。Bob 需要查詢提交內容，才能開始批改。 因此查詢學生提交的 Read Model 是批改作業這個 Command 的前置動作。

因此你的事件風暴模型可以長成這樣：

```
[Read Model]          [Actor]         [Command]
GetSubmission    →   老師 Bob    →   IssueVerdict
查詢學生提交                          批改作業
      ↑ 根據              ↓ 執行
```

Bob 看到 Alice 的提交後，決定批改。

**2.2 Command：批改作業**

那麼在批改作業之後啊，接著，系統會去看說本次批改是否有符合規則，如果有的話，就會改變系統狀態，更新批改記錄和課程進度的狀態聚合，最後產生「批改完成」的事件。

```
[Command]           [Rules]                     [Aggregate]
IssueVerdict   →   Preconditions:           → ChallengeSubmission
批改作業            • 老師有權限                + LessonProgress
                    • 提交記錄存在              • verdictRank: MASTERY
                    • 尚未批改或可重新批改       • status: COMPLETED
     ↓ 通過：改變狀態                               ↓ 產生
                                                [Event]
                                              VerdictIssued
                                               批改完成
```

#### Step 3：學生查詢結果 → 交付課程

**3.1 Read Model：學生查詢批改結果**

Alice 收到通知，作業已批改。她需要查詢批改結果，確認自己的作業通過了，才能去交付課程。 因此查詢批改結果的 Read Model 是交付課程這個 Command 的前置動作。

因此你的事件風暴模型可以長成這樣：

```
[Read Model]           [Actor]         [Command]
GetLessonProgress  →  學生 Alice   →  DeliverLesson
查詢批改結果                           交付課程
       ↑ 根據              ↓ 執行
```

Alice 看到課程已完成，決定交付課程，獲得經驗值。

**3.2 Command：交付課程**

那麼在交付課程之後啊，接著，系統會去看說本次交付是否有符合規則，如果有的話，就會改變系統狀態，更新課程進度為已交付並增加使用者經驗值，最後產生「課程已交付」的事件。

```
[Command]           [Rules]                     [Aggregate]
DeliverLesson  →   Preconditions:           → LessonProgress + User
交付課程            • 學生有權限                • status: DELIVERED
                    • status = COMPLETED        • User.exp: +100
                    • 尚未交付
     ↓ 通過：改變狀態                               ↓ 產生
                                                [Event]
                                              LessonDelivered
                                               課程已交付
```

## 六、系統邊界模型（終於要來聊聊：怎麼翻譯成規格）

好，我們理解了 Event Storming 的核心元素、橋樑作用，以及完整的流程建模。現在讓水球我把這些元素組合起來，找到裡面最關鍵的部分，構成你撰寫規格時需要參考的模型。

這個模型叫做**系統邊界模型**（System Boundary Model）。

### 模型結構

Event Storming 模型中有兩種 Actor 會關注的「操作」，對應**兩種系統邊界模型**。

「**系統邊界**」的意思**就是任何 Actor 可以與該系統「互動」之處**，所有的互動時機點所構成的邊界。

**這件事非常重要，因為只要你能清楚用「規格」描繪這些互動的規則，就能讓 AI 幫你精準開發出來。**

那主要就兩種系統邊界模型，也就是說啦 Actor 主要與系統的互動，就只有兩種而已～！

結合事件風暴的術語來說：一種就是「修改 (Command)」，另一種就叫「查詢 (Read Model)」。 非常直觀來說，就是 **你的系統要嘛給人「改」，要嘛給人「查」**。

**1. 修改型操作（Command Operation）**

首先是 Command，如果把 Command 當成是用戶可以與系統互動的邊界，那我們得到這個模型：

但其實系統之間的互動方式，不一定只有 Command。在比較複雜的分散式系統架構設計中，有些系統會透過「偵聽 Event」，當該 Event 發生時，進行相對應的處理。 所以系統之間有可能透過 Event 來非同步互動。

好比說，水球軟體學院課程平台用的「第三方金流」，會需要設定「當用戶付款完之後，要呼叫哪個 Webhook URL」，這某種程度上就是去偵聽「付款事件」的意思，第三方金流透過 Event 來與我的系統互動。

因此這個系統互動的邊界模型，在修改型操作中也要把 「偵聽 Event」 考慮進去：

白話文：如果修改成功，那就會改變系統狀態、產生事件。

**2. 查詢型操作（Query Operation）**

查詢比較單純，就是用戶向系統請求查詢。

白話文：如果查詢成功，那就會回傳查詢資料 (Read Model)。

你看到差異了嗎？

來，我們來看看這兩種流程。

### 修改型操作：模型流程說明

這個模型描述了系統的邊界：從 Command 進入，經過 Rules 檢查，改變 Aggregates 狀態，達到 Postconditions，最後 raise Event。

### 查詢型操作：模型流程說明

查詢型操作比較簡單，它只需要檢查權限（Preconditions），然後回傳資料（Read Model）。

查詢型的 Preconditions 通常較簡單，主要是權限驗證，不像修改型需要複雜的業務規則驗證（如單調遞增、狀態一致性等）。

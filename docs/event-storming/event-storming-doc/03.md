## 一、為什麼需要從 Event Storming 翻譯到 Gherkin？

### Event Storming 建立了橋樑，但離規格驅動開發還剩下最後一步

你還記得嗎？Event Storming 模型幫我們建立了系統邊界模型，連接了 Problem Domain 和 Solution Domain。但這個模型有個限制——它還不是**可執行**的**測試案例**。

好比說，我們在 Event Storming 模型上點出了各種要素：

**修改型操作的要素**：

這些要素定義了「使用者如何增加影片進度」的完整業務規則。

**查詢型操作的要素**：

這些要素定義了「使用者如何查詢進度資訊」的完整業務規則。

這些要素很棒，大家都能理解。但問題是啊：

**「這些要素能直接執行嗎？能作為自動化測試，來自動驗證系統是否符合規格嗎？」**

當然不行，畢竟事件風暴這只是系統的建模而已，還沒有被翻譯成所謂的「測試案例」，沒辦法去自動驗收系統是否符合規格。

Event Storming 模型只是一個視覺化的討論結果：它幫助我們理解業務邏輯，但它沒有標準格式可供機器解析和執行。這些要素還停留在「人類可讀」的層次，無法被自動化測試工具直接使用。

要讓這些規格變得可執行，我們需要一個結構化的、機器可讀的語言——這就是 Gherkin 登場的時候囉～

## 三、Feature 切分與 Rule 設計原則

在開始應用翻譯規則之前，我們需要先理解兩個重要的架構設計原則：Gherkin 的 Feature File 該如何切分？Rule 該如何設計？

這些原則會影響你的 Feature File 組織結構，不過**修改型和查詢型操作都適用同樣的原則**，規則滿簡單的。

### Feature 切分粒度：每一個 Command/Query 都要獨立寫成「一個 Feature File」

**核心原則**：一個 Command = 一個 Feature File，一個 Query = 一個 Feature File。

為什麼這樣切分？簡單來說啊，那當然就是因為，每個 Command 和 Query 都會是系統要支援的一種功能嘛。 系統要嘛給人查、要嘛給人改，那每種「查詢操作 (Query)」和每種「修改操作 (Command)」當然都要獨立被撰寫成一個 Gherkin Feature File。

## 四、修改型操作的特有翻譯規則

修改型操作有兩個特有的元素需要翻譯：

這兩個元素是修改型操作的核心，也是它跟查詢型操作最大的差異。

### 4.1 Event 的翻譯

**Event** 在 Gherkin 中主要出現在兩個位置，取決於它的來源：

#### 本系統產生的 Event → Then

當我們測試一個 Command 時，系統可能會產生 Event。這時 Event 出現在 Then，用來驗證「這個 Event 有沒有被觸發」。

**WSA 範例：AddVideoProgress**

注意 (Spec by Example 原則）：Event 的驗證也要帶上實際的資料，帶上重要的「預期的值」（如 課程Id），不能只寫「事件應被觸發」，還要指定清楚事件觸發時，課程 ID 應為多少。

#### 外部系統餵入的 Event → When

在微服務架構中，系統之間經常需要互相溝通。好比說，在 WSA 中，訂單系統可能需要監聽支付系統發出的 `PaymentCompleted` 事件——當支付完成時，訂單系統要自動更新訂單狀態。

這種情況下，Event 出現在 When，表示「外部系統餵入了這個 Event」：

為什麼要標註「事件：」？因為這樣可以清楚區分「用戶執行操作」和「系統監聽到事件」。這在微服務架構中特別重要。

### Event 是用在跨系統、服務的規格驅動開發中

這門課前期不會提到太多分散式系統、微服務之間規格驅動開發的事，畢竟如果連單體都尚未征服的話，聊分散式系統言之過早。

不過上一個單元（第二單元）撰寫的目的是以「完整」為主，讓一些熟悉進階架構的人可以提早有完整的啟發，因此我仍必須在此先讓你知道，為什麼 Event 這個元素很重要，會在哪裡被用到。

對於比較不熟悉微服務或是 CQRS 架構的軟工夥伴而言呢，不用擔心。實際上，在本課程後續章節我們所提到的一般的單體服務的規格驅動開發中，由於沒有跨系統的互動和邏輯驗證，因此都用不到 Event 這個元素，你可以等用到的時候再回過頭來看。

#### 進階：Event 也可以出現在 Given

除了 Then 和 When，Event 其實還可以出現在 **Given** 中，這是比較進階的用法。

**Event in Given 適用於兩種情境**：

**情境一：修改型操作接收外部事件**

當你的系統需要接收來自第三方系統的事件（如金流通知、物流更新），並基於這些事件執行 Command，這時 Event 出現在 Given 用來建立「系統已接收到外部事件」的前置狀態。

這個範例中，Given 使用 Event 來模擬「第三方金流已經通知我們付款成功」的狀態，然後 When 執行完成訂單的 Command。

**情境二：查詢型操作的事件驅動架構**

在某些架構中（如 CQRS），查詢服務的 Read Model 是透過監聽事件來建立的。這時 Event 可以出現在 Given，用來建立查詢測試所需的前置狀態。

查詢端不處理 Commands，而是監聽 Events 來建立查詢用的資料。

這部分的詳細說明和完整範例，請參考「六、實踐選擇（Practice Choices）」中的「Given 的三種寫法」。

## 七、用「Key」來識別 Aggregate 或 Actor

### Given 的 Key 識別規則

在 Gherkin 中，你必須在每一個步驟的敘述中，都辨識清楚此敘述到底指的是哪一個 Aggregate 或 Actor。 為了明確辨識 Aggregate / Actor 的身份，我們稱這個辨識用的屬性為「Key」（身份識別屬性）。

我們不稱之為 "ID" 的原因是因為，在撰寫 Gherkin Feature File 的時候，很多時候你不會想要在規格中一直用 "ID" 去做辨識， 你會想要用更有親和力、但同樣也有基本辨識度的其他屬性辨識 Aggregate / Actor。

### 複合 Key 的表達方式

有時候，一個 Aggregate 的 Key 是複合的（由多個欄位組成）。 好比說，`LessonProgress` （課程進度）的 Key 是 `userId + lessonId` （哪個用戶學員，在哪個課程上的進度）。

「課程進度」這類型的資料本身，他的辨識度並不是來自於一個 ID，而是來自於多個 Aggregates 之間的「關聯」。 好比說啊，課程進度——就是「課程」和「用戶學員」的關聯，因此課程進度的 Key 就會是「課程的 Key 加上用戶學員的 Key 」組合而成，這就叫「複合 Key」。

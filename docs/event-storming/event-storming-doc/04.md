## 一、DSL-Level Gherkin 的局限

### 想要 AI 自動生成測試程式碼？先等等...

上一個單元我們學會了把 Event Storming 翻譯成 Gherkin Feature File，翻譯成 Gherkin 之後就能用 Given/When/Then 這種更容易「舉例說明」的格式來描述系統的實際行為。

這個「Gherkin」在整個規格光譜的翻譯鏈上，究竟是哪一個位置呢？

水球我把這個從 Event Storming 直接翻譯而成的 Gherkin 定位叫做「**DSL-Level Gherkin / DSL-Level Feature File**」。

之前有提過，但這邊再重新解釋一次，**為什麼叫做 DSL-Level Gherkin** 呢？

首先， DSL 全名就是 Domain-Specific Language（領域特定語言），意思是「專注在業務領域的語言」，用業務人員看得懂的語言來描述系統行為。白話文就是「行話」的意思。

因此，DSL-Level Gherkin 就是一種讓業務人員、測試人員、開發人員都能看懂的「Gherkin Language」所構成的規格。

這份規格同時代表業務流程又能同時被開發解析成系統的初步設計，這還挺不錯的，對吧？

**但是啊**，這樣就做得到「規格驅動全自動開發」了嗎？雖然大致上能做到更可靠的高度自動化了，但是還不夠。

那麼，**DSL-Level Gherkin 是否能被精準翻譯成測試的程式碼**呢？

如果你現在跟 AI 說：「請你幫我從這個 DSL-Level 的 Feature File 規格生成測試程式碼」的話，會發生什麼事情？

那當然，**AI 在把 DSL 翻譯成測試程式碼的過程中一定會有腦補的，因為 DSL-Level Gherkin 的語法還是太高階了，無法直接映射到技術的實作上**。

AI 並不會回過頭向你澄清技術問題，它會「自行隨意腦補」技術實作細節，然後給你一個看似合理、但可能完全不符合你系統架構的測試程式碼。

## 二、ISA-Level Gherkin：測試程式碼的抽象

### 解決之道

還記得先前提到的「規格的光譜：翻譯鏈」嗎？

我們已經走到了第二步（DSL-Level Gherkin），現在要進入第三步：**ISA-Level Gherkin**。

### 什麼是 ISA？

ISA = **Instruction Set Architecture**（指令集架構）

這個詞來自計算機架構，原意是「計算機處理器可以執行的指令集」。

在規格驅動開發中，ISA 是：

> **測試程式碼的抽象。基於特定 Tech Stack，參數明確，可被 100% 精準翻譯成測試程式碼。**

簡單來說，ISA 就是「讓 AI 知道如何精準翻譯成特定技術場域下，其對應『測試程式碼』的規格」。

## 總結

好，咱們這個單元學了很多東西。來，讓水球我幫你整理一下。

### 核心要點

一共濃縮成四個核心要點：

1. **DSL-Level Gherkin 的局限**，DSL 無法 100% 精準翻譯成測試程式碼，因為 (1) 缺少技術操作（DB 插入、API 呼叫、DB 查詢），(2) 隱藏技術參數（用 friendly Key 如 "Alice"，隱藏技術 ID 如 userId: 123）

2. **ISA = 測試程式碼的抽象**，ISA 基於特定 Tech Stack，參數明確，可被 100% 精準翻譯成測試程式碼。它就像組合語言，介於高階語言（DSL）和機器碼（Test Code）之間。

3. **ISA 的兩種風格**，(1) 指令集包裝版（可讀性佳，需要 isa.yml），(2) 明確技術參數風格（所有技術細節明確，不需要 isa.yml，但步驟冗長）。本課程推薦使用指令集包裝版。

4. **ISA 需要其他規格檔支援**，(1) isa.yml 定義指令集句型和語意，(2) API Spec 定義 API 技術細節（endpoint, request/response schema），(3) DBML Spec 定義 DB 結構（table, 欄位, 型別）。三者各司其職，可重用、易維護。

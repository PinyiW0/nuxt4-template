# TDD 循環基礎概念：先畫靶後射箭

各位規格驅動全自動開發術的魔法初學者們好！

在前面的章節中，我們學會了如何用 Event Storming 建立系統邊界模型，並將它翻譯成 Gherkin 規格。現在你手上已經有了一份完整的 DSL-level Feature File，接下來要做什麼？

**直接把規格丟給 AI，請它一次全部開發出來？**

不，這不是可靠的工程方法。

很多人會這樣想：「我都把規格、規則寫得這麼清楚了，AI 應該可以一次到位吧？」但實際上，這樣做會遇到一個根本性的問題：**AI 模型不是萬能的，AI 就像是一個注意力不集中的孩子，你給他越多資訊他很有可能會失焦，搞不清楚重點，或是忘東忘西**。

什麼意思？當你要求 AI 一次做太多事情——既要理解整份規格，又要設計資料結構，又要實作所有功能，又要處理各種邊界條件——**AI 很容易失焦、分心**。更麻煩的是，**一旦 AI 分心了，它沒有能力自己把自己拉回來**。它不會停下來說「等等，我好像偏離主題了」，而是會繼續產出看似合理、實則偏離目標的程式碼。

這就像是你同時交代一個人十件事，最後可能十件都做得不夠好。

那該怎麼辦？**答案是：分割擊破。**

你必須把大任務切成小任務，讓 AI 一次只專注在一個面向上。只有這樣，AI 才能做到高精度的開發。無論是撰寫測試程式碼，還是實作功能，都是一樣的道理。

但這裡有個關鍵前提：**要能切分任務，你自己必須先有知識量**。

你必須了解：

**如果你不懂開發流程，你就無法有效地切分任務，也就無法駕馭 AI 進行高品質開發。**

這就是為什麼我們要學習 **AI x 測試驅動開發（AI x Test-Driven Development, AI x TDD）**。

TDD 本身就是一套簡單的任務切分方法。它把「軟體開發」這個大任務，拆解成三個清晰的小步驟，在這三個步驟中快速循環即可構成完整的軟體開發：

每個步驟都有明確的目標，每次都只專注在一件事上。

如果你學會透過 TDD 的方式「引領自己」，那你才有能力有條有理地「引導 AI」，逐步地、可靠地把功能開發出來。

在軟體工程中，**可靠性來自於「有條有理」的翻譯實踐——每一步翻譯走得越謹慎，品質就越高**。

Ok，所以說「測試驅動開發」又要怎麼進行才好？

**從寫測試開始。**

> **TDD 的核心精神：先畫靶，後射箭。**

「先畫靶後射箭」這句話，你可能在目標管理或專案管理的書籍中看過。但對工程師來說，這句話有更深一層的意義。

為什麼？因為**工程師很容易陷入細節之中**。

我們都有工匠精神——寫程式時，會在意這個函數命名是否夠好、這段邏輯是否夠優雅、這個設計模式是否夠完美。我們會對細節有自己的堅持和要求。這本身不是壞事，但問題是：**我們很常在細節中失焦，忘記真正的目標是什麼。**

你可能也有過這種經驗：

我們會焦慮：「這樣寫會不會有維護性問題？」「未來如果要擴充怎麼辦？」「這個設計夠不夠彈性？」

這些都是工匠的完美主義在作祟。

**但我們需要從完美主義中得到救贖。**

在傳統的開發流程中，我們習慣先寫程式碼，寫完之後再補測試（如果有補的話）。

但這就像是先射箭，然後在箭落下的地方畫靶——當然每次都會命中！**但問題是：你真的射向正確的方向了嗎？你真的滿足了需求嗎？還是只是滿足了你自己對「完美程式碼」的想像？**

這種開發方式容易導致：

TDD（Test-Driven Development，測試驅動開發）反轉了這個順序：**先定義預期行為（寫測試），再實現行為（寫程式碼）**。

這就像先畫好靶，再瞄準射箭。

**TDD 是最簡單的、能夠幫助你做到「先求有再求好、先畫靶後射箭」的開發流程。只要上述剛剛提到的三個步驟就能實現 TDD 循環。**

讓我們繼續展開看看這三個步驟是什麼。

## 一、TDD 的三步驟：Red-Green-Refactor

TDD 是一個簡單但強大的三步驟循環：

```
🔴 Red        🟢 Green       🔵 Refactor
  紅燈    →     綠燈      →     重構
(先寫測試)   (最小實作)     (改善品質)
```

簡單來說：

讓我們深入了解每個步驟：

### 🔴 紅燈（Red）：先寫測試

第一步是寫一個會失敗的測試 (Failing Test)。

為什麼要讓測試失敗？

因為測試驅動開發是**先寫測試**，那麼，這時候功能都還沒實作呀，所以測試執行時當然會失敗，這是正常的！

紅燈代表「測試寫完啦，但是實作還沒完成」，提醒你接下來要實作功能。

### 🟢 綠燈（Green）：寫最少的程式碼讓測試通過

第二步是寫剛好足夠的程式碼，讓測試通過。注意這裡的關鍵詞：**剛好足夠**。

### 🔵 重構（Refactor）：在測試保護下改善程式碼

第三步是在測試的保護下，安全地進行重構。

**什麼是重構？** 重構的意思是**行為不變，純粹改善程式碼的結構**。你不是在加新功能，也不是在修 bug，而是讓程式碼變得更好讀、更好維護。

## 二、為什麼要 TDD？

你可能會問：「直接寫程式碼不是更快嗎？為什麼要先寫測試？」

讓我們看看 TDD 帶來的三大價值：

### 1. 測試作為規格（Specification）

測試是最低階、最精準的可執行規格文件，它明確定義了「系統應該做什麼」。

為什麼說測試永遠不會過時？

因為測試程式碼和產品程式碼會**一起進行版本控制**。每一次有新的版本提交時，都會：

這樣可以確保測試和程式碼**同步更新、高度一致**。如果你把測試程式碼視為「最低階、最精準的規格」，那它就是永遠不會過時的活文件。

### 2. 測試作為回歸保護（Regression Protection）

每次修改程式碼時，測試會自動驗證是否破壞了原有功能。

```
修改程式碼 → 執行測試 → 測試通過？
                         ├─ Yes → ✅ 安全，沒有破壞功能
                         └─ No  → ❌ 警告，破壞了原有功能
```

### 3. 測試作為設計工具（Design Tool）

寫測試的過程，會迫使你思考 API 的設計。

**如果測試很難寫，通常代表設計有問題**：

TDD 引導你設計出更簡單、更容易測試的程式碼。

## 三、最小增量原則：每次都只寫剛剛好的程式碼來通過測試！

TDD 的核心原則之一是**最小增量開發（Minimal Incremental Development）**：

> **Write Just Enough Code to Pass the Test**（寫剛好足夠的程式碼讓測試通過）

讓我們透過兩個簡單範例來體會這個原則。

所以，請牢記 TDD 精神：「測試在先，重構在後」。等測試綠燈時再安心動手，這不僅讓你在重構時更有自信，也確保系統品質不斷提升。

## 六、TDD 的迭代節奏

讓我們總結 TDD 的完整迭代節奏：

```
開始開發新功能
      ↓
閱讀 Gherkin 規格
      ↓
選擇一個 Rule
      ↓
🔴 紅燈：寫測試（定義預期行為）
      ↓
執行測試 → 測試失敗？
              ├─ No → 檢查測試是否寫對
              └─ Yes ↓
🟢 綠燈：寫程式碼（最小實作）
      ↓
執行測試 → 測試通過？
              ├─ No → 繼續修改實作
              └─ Yes ↓
🔵 重構：改善程式碼（保持綠燈）
      ↓
Git Commit（記錄迭代）
      ↓
還有 Rule？
  ├─ Yes → 回到「選擇一個 Rule」
  └─ No  → 完成功能
```

### 核心原則回顧

1. **一個測試對應一個迭代**

2. **每個迭代完成一個小目標**

3. **寫剛好足夠的程式碼**

### 為什麼 AI 時代的 TDD 可以不一樣？

你知道嗎？傳統的測試驅動開發，是在**沒有 AI 的時代**發展出來的。那時候，開發者只能靠自己的腦袋去設計、去思考，所以必須採用「最小增量」的方式，一次只做一點點，小心翼翼地往前推進，在這個過程中慢慢找到那種「穩定、成熟」的工程感覺。

這是一種**保守而嚴謹**的迭代方法，因為人腦的負荷有限，一次思考太多東西容易出錯。

但是，現在有 AI 了，遊戲規則完全改變了。

說實在的，**AI 的大規模思考效率，遠遠超過人類**。它可以同時處理多個測試案例、多個業務規則、多個邏輯分支，而且品質是一定程度可控的。這是人類很難做到的事情。

因此啊，**以前人類自己做 TDD 也許要追求小步慢行，但有了 AI 後就不一定真的必要走得這麼「小步」了。**

### AI 的獨特優勢：無情的效率

AI 和人類有一個根本的不同：**AI 非常「無情」，是一種大規模效率的無情**。

什麼意思呢？

人類在開發時，很容易在一個小範疇裡就開始擔心、開始焦慮：

這些焦慮會拖慢我們的速度，讓我們不敢一次做太多事。

### TDD 的四個階段（分成四個 Prompts）

我把 AI x TDD（測試驅動開發）分成四個階段，每一個階段由一個 Prompt 充分交代，因此底下就是先向你說明每一個 階段/Prompt 的效果。

**等等，為什麼要有「樣板生成」這個階段？**

你可能會好奇：傳統的 TDD 明明就只有三個階段，紅燈、綠燈、重構，為什麼這裡多了一個「第 0 階段：樣板生成」？

這是因為**與 AI 協作有一個關鍵原則**：你可以試著把大的任務拆成小的任務，讓 AI 一次專注在一個**專心的面向**上，這樣它產出的品質才會有高度的穩定性和精度。

讓我們來想想：TDD 的第一步是什麼？**紅燈階段——撰寫測試程式碼。**

這一步真的是超級無敵關鍵！**如果測試程式碼寫錯了，後面驅動出來的程式碼也會是錯的**。而且你想想，code review 的成本這麼高，我們是不是寧願把「寫測試」這個動作拆成兩個步驟，而不要一次到位？

**所以我的做法是這樣的**，把 TDD 的「紅燈環節」切成兩個步驟：

- **第一步（樣板生成）**：只生成測試程式碼的骨架
- **第二步（紅燈階段）**：才實作測試的具體邏輯

**這樣做的好處**：

所以，傳統 TDD 的「紅燈」階段，在 AI x TDD 中被拆成了兩步：**樣板生成 + 紅燈實作**。

#### 🔴 Prompt 1：紅燈（Red Phase）

**目的**：為每一個測試函數，去實作測試邏輯，並確保測試失敗 (Failing Test)

**紅燈階段會做什麼？** 把測試骨架變成真正的測試程式碼，並定義空的介面。

在紅燈這個階段，我們的 Prompt 有精心調整過。我們不只是跟 AI 說「請你去實作每個測試程式」，因為如果只是這樣講，沒有定義清楚「實作測試的邊界」在哪裡，你往往會遇到一個問題：

**寫測試的時候，AI 肯定就必須要先去定義一些介面/類別/模組出來，要不然測試程式碼在執行時就會因為介面/類別/模組未定義而出錯。**

好比說，如果你今天是跟訂單相關的功能，你在寫測試要測訂單功能時，難道你不用先開好訂單相關的類別嗎？

可是，如果 AI 真的去寫這些 `Order` 或 `OrderService`，這時候就會有一個問題：**你得跟他說清楚，他能寫多少？如果沒講清楚，AI 很有可能會失焦而不小心把整個業務邏輯都實作完了。**

**如果他實作了邏輯，那不就違反了紅燈的原則嗎？** 紅燈階段不應該實作業務邏輯，測試應該要失敗才對。

**所以我們在紅燈的 Prompt 裡面有特別寫清楚**：

**✅ 你可以做的事情**：

**❌ 你不可以做的事情**：

**這個邊界的定義非常重要**！

Prompt 裡面會有「你可以做什麼、你不可以寫什麼」的撰寫，都是在描述**實作測試的範疇到哪裡**。

並不是代表你完全不可以去寫產品的程式碼。因為資料結構你還是要定義——比如說**訂單的資料、訂單欄位有哪些，這個你還是要定好**。這些也不是測試程式碼，你總要先把它定好，測試才能跑起來。

**總結紅燈階段的範疇**：

這樣的設計，讓 AI 專注在「定義測試所需的結構」，而不會一口氣做太多事情，也確保了我們遵守 TDD 的紅燈原則。

# TDD 綠燈階段：讓測試通過

## 目標

在 TDD 紅燈階段已經寫好測試並確認失敗（紅燈 🔴）。現在進入綠燈階段：

**寫最少的程式碼讓測試通過，不斷 trial-and-error 直到所有測試變綠。**

---

## 核心原則

### 1. 最小增量開發原則

只寫讓測試通過所需的最少程式碼，不要多做。

**範例 (Python)**：
```python
# ❌ 做太多了（測試沒要求）
def add_item(product_id, quantity):
    validate_product_exists(product_id)  # 沒測試
    log_operation(product_id)            # 沒測試
    send_notification()                  # 沒測試
    self.items.append(...)

# ✅ 剛好夠（只實作測試要求的）
def add_item(product_id, quantity):
    self.items.append({"product_id": product_id, "quantity": quantity})
```

### 2. Trial-and-Error 流程

```
1. 執行測試 → 看哪個失敗
2. 寫最少的程式碼修正
3. 執行測試 → 還有失敗？
4. 重複 2-3，直到全部通過
```

**不要一次寫完**，讓測試驅動你一步步完成。

## Service / Repository 職責分配

### Repository 職責：資料存取

- 負責儲存、查詢、刪除資料
- 只管資料的 CRUD，不管業務邏輯

**實作策略（根據專案情況）：**

#### 情況 1：專案使用 ORM

Repository 作為 **Adapter**，封裝 ORM（Adaptee）的使用邏輯。

**範例 (Python with SQLAlchemy)**：
```python
# Repository 是 Adapter，封裝 ORM
class OrderRepository:
    def __init__(self, session):
        self.session = session  # ORM session (Adaptee)

    def save(self, order):
        """封裝 ORM 的儲存邏輯"""
        self.session.add(order)
        self.session.commit()

    def find_by_id(self, order_id):
        """封裝 ORM 的查詢邏輯"""
        return self.session.query(Order).filter_by(id=order_id).first()
```

#### 情況 2：專案沒有 ORM

直接實作 **Fake Repository**，用記憶體內的資料結構（如 dict、map、hashmap）模擬 DB 操作。

**範例 (Python)**：
```python
# Fake Repository，模擬 DB 操作
class OrderRepository:
    def __init__(self):
        self.orders = {}  # 用 dict 模擬資料庫

    def save(self, order):
        """模擬儲存到資料庫"""
        self.orders[order.id] = order

    def find_by_id(self, order_id):
        """模擬從資料庫查詢"""
        return self.orders.get(order_id)

    def find_by_customer(self, customer_id):
        """模擬複雜查詢"""
        return [o for o in self.orders.values() if o.customer_id == customer_id]
```

**關鍵原則**：無論使用哪種方式，Repository 的介面（如 save、find 等方法）保持一致，Service 不需要知道底層實作細節。

### Service 職責：業務邏輯

- 負責實作業務規則和流程
- 透過 repository 讀取和儲存資料
- **必須支援依賴注入**（測試才能注入 repository）

**範例 (Python)**：
```python
class OrderService:
    def __init__(self, order_repository=None):
        # 支援依賴注入
        self.order_repository = order_repository or OrderRepository()

    def create_order(self, customer_id, amount):
        # 業務規則檢查
        if amount <= 0:
            raise InvalidArgumentError("金額必須大於 0")

        # 業務邏輯：創建訂單
        order_id = generate_order_id()
        order = Order(order_id, customer_id, amount, status="待付款")

        # 透過 repository 儲存
        self.order_repository.save(order)

        return order_id

    def cancel_order(self, order_id):
        # 透過 repository 讀取
        order = self.order_repository.find_by_id(order_id)
        if not order:
            raise OrderNotFoundError("訂單不存在")

        # 業務規則檢查
        if order.status == "已完成":
            raise InvalidStateError("已完成訂單無法取消")

        # 業務邏輯：修改狀態
        order.status = "已取消"

        # 透過 repository 儲存
        self.order_repository.save(order)
```

### 為什麼需要依賴注入？

**讓測試和 Service 使用同一個 repository 實例。**

**範例 (Python)**：
```python
# 測試檔案
def test_創建訂單():
    # 1. 創建 repository
    repository = OrderRepository()

    # 2. 注入到 service
    service = OrderService(order_repository=repository)

    # 3. 執行操作
    order_id = service.create_order("C001", 1000)

    # 4. 透過同一個 repository 驗證（關鍵！）
    order = repository.find_by_id(order_id)
    assert order.status == "待付款"
```

如果不支援依賴注入，測試和 Service 會使用不同的 repository，測試就無法驗證狀態變化。

## 完成條件

綠燈階段完成的標準：

- ✅ 執行測試框架，全部測試通過（綠燈 🟢）
- ✅ 沒有編譯/執行錯誤
- ✅ 程式碼簡單直接

**不需要**：
- ❌ 程式碼優雅（留給重構階段）
- ❌ 效能優化（留給重構階段）
- ❌ 完整錯誤處理（測試沒要求就不做）

---

## 記住

1. **測試驅動你** - 不要猜測需要什麼，讓失敗的測試告訴你
2. **最小實作** - 只寫通過測試需要的程式碼
3. **依賴注入** - Service 必須支援注入 repository
4. **Trial-and-Error** - 執行測試 → 修正 → 再執行，不斷循環

完成綠燈後，進入重構階段 ♻️
